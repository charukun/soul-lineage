# 序破急バトルシステム — 品質・可愛さを守る段階統合計画

策定日: 2026-09-21

## 目的と最優先条件

「戦闘演出2」の正式名称を **序破急バトルシステム** とする。現在のこのシステムの品質・可愛さを最重要の基準とし、旧戦闘システム（ユーザー呼称「戦闘演出1」、一覧上は「戦闘演出」）で整備中の百年転生のゲーム仕様を、一機能ずつ取り込む。

**旧画面へ新側を寄せるのではなく、新側のキャラ・動き・空気感を維持して、百年転生のルールを接続する。機能数を増やしても可愛さ・見やすさ・動きが後退した変更は採用しない。** この計画は新しいゲームルールを勝手に確定する文書ではない。

## 変更してはいけない基準

キャラクターの頭身、顔・輪郭、サイズ感、素材・配色、装備との一体感を守る。待機・歩き・攻撃・被弾・倒れる動きの繋がりを守り、Tポーズ、足滑り、急な姿勢切替、武器ずれを増やさない。カメラの距離・角度、視界、背景の密度、暖冷の光、影、霧、発光を機能追加のついでに変えない。

キャラが読めるエフェクト量、ヒットの手応え、音と動作の同期を守る。部位負傷を取り込む際も、欠損表現や極端なモデル変形を追加しない。HUDで顔や動作を隠さず、Web管理画面のような常設パネルを積み上げない。レビューの選択グリッドは既存の5列を維持する。

既存の入力・移動・自動戦闘を尊重し、通常攻撃ボタン、反射神経前提の回避操作、QTE等を移植の都合で追加しない。新側は現時点で操作パネルなしの演出面であり、本編入力の接続は専用段階で行う。

素材は現行manifestと自前Static Asset Originを維持する。第三者runtime URLへの差替え、proxy形状への置換、品質低下による軽量化を行わない。素材追加が必要になった段階だけ、既存のライセンス・作者・原典・revision・hash・byteLength記録とmaterialize経路を使う。

## 段階計画と完了条件

各段階は必要に応じて複数の小さいPRに分ける。以下の後続段階は計画であり、P0の改名だけで完了扱いにしない。

| 段階 | 実施内容 | 完了条件 |
| --- | --- | --- |
| P0 原型保護・正式命名 | 名称統一、bkと原型SHAの保存、変更禁止条件・本計画・同一性検査を追加 | 名称以外のHTML、native runtime、CSS、音、環境、素材manifestと依存lockfileが基点と同一。旧側とbkを保持 |
| P1 差分台帳・読取専用の接続 | 旧側を機能ごとに「確定/調整中/レビュー専用/本編未接続」に分類。stateとeventの最小契約、actor ID、battle ID、乱数・時間の所有者を決める | bridge無効時は原型と同じ挙動。読取だけでseed消費・damage・保存・描画を変えない。app間importを作らない |
| P2 序破急・意識駆動 | 正式な序/破/急の編成・遷移を接続し、意識バランスが接近・間合い・攻め/守り・反撃の選択へ作用するようにする | 同じ初期条件で意識の違いが実行動に現れる。段階表示は実行状態由来。既存モーションへの対応を一本ずつ検証し、演出のテンポを無断変更しない |
| P3 部位・スタミナ・勝敗 | 六部位の耐久/負傷、行動能力、スタミナ・休息、戦闘不能と戦闘結果を接続 | 一命中につきdamage/負傷を一度だけ適用。負傷→行動への影響→休息/治療を検証。数値表示と実体が一致し、可愛いモデルを壊さない |
| P4 技・装備・発見の整合 | 正式catalogに基づく心・技・体・装、技/段/連、武器別モーションを取り込む。閃き・技名・秘技/奥義の正式contractを確認する | catalogにない技をUIで生成しない。技の習得、編成、試演、発動を区別。レビュー上の閃き演出だけで本編の習得済みを書き換えない |
| P5 遭遇・人数・本編操作 | タイマンから複数敵・味方へ拡張し、接近戦闘・移動・離脱・ターゲット/障害物の扱いを本編へ合わせる | 実際に届いた攻撃だけが当たり、対象や部位を取り違えない。敵増加時もキャラと攻撃を読める。デモのwaveループを本編へ強制しない |
| P6 人生・保存との接続 | 年齢、装備資格、遠征/帰還、救助、寿命/転生、保存/再開をcanonical commandへ接続 | 生活→支度→戦闘→結果→帰還/救助→再開を通常操作で一巡。時計加速で戦闘を加速しない。転生・再開時に状態や報酬を二重適用しない |
| P7 総合受入・本編への採用 | 新演出と本編domainの統合、端末検証、長時間/連戦検証、切替と戻し方を確定 | 品質・可愛さ、ゲーム契約、保存、安全な切替の全条件を満たす。旧側は必要な比較期間維持。Production変更は別途明示許可の範囲だけ |

P1の最初の成果物は差分台帳と非侵襲の契約テスト。まだ使わない大きなframeworkや空のadapterを先に量産しない。P2以降も、ロジック接続と大きな見た目改変を同じPRへ混ぜない。

## 接続方式

百年転生のdomain/command → snapshot・semantic event → 新側presentation adapter → 現行のキャラ・モーション・VFX・音、という一方向を基本とする。共通化するdomainは適切な `packages/` へ抽出し、`apps/review` から `apps/rinne` をimportしない。旧コード全体を別appへコピーして二重管理しない。

命中判定、HP、部位、スタミナ、技の合法性、勝敗は一つの権威だけが決定する。新旧のsimulationを同時に本番stateへ書かせない。比較用shadow実行を作る場合も、乱数・保存・音・エフェクト・報酬へ副作用を出さない。

接触とモーションの対応では、技ID・対象ID・攻撃インスタンスID・実行段階・命中窓を明示し、同じ命中を二度描画/適用しない。旧側の抽象poseをそのまま新モデルに流さず、既存clipとtransitionへ対応付ける。未対応技は未対応として検出し、無関係なモーションで成功を装わない。

## 本編仕様として必ず守る項目

基点の `MAIN_GAME.md` で確認した契約: 0歳開始、60秒/年、100歳の生涯、武具7歳、遠征15歳、5世界年ごとの出航、生活行動8実秒。世界時計の1/5/10/20倍を移動・戦闘・生活行動の実秒へ掛けない。数値や解禁条件は新側で独自定義せず正本を参照する。

装備はUIによるstate直書きではなく、年齢・生存・村内・非戦闘・近接・所持等をcommand側で再検証する。現行catalogの候補表示と、能力解禁・閃きの採用状況を混同しない。旧レビューの閃き実演と、本編で現在有効な習得条件の差をP1/P4で確認する。

転生では年齢・体力・傷・装備・持ち物・編成・生涯経験を基礎状態へ戻し、一族記録と帰還して刻んだ故郷を残す。保存はcanonical stateを扱い、演出途中のpose・VFX・音を永続化しない。戦闘途中の再開では敵の体力/戦闘不能等を正しく復元し、同じ被弾・報酬を再適用しない。solo/sharedの停止と時計権限、排他制御、壊れた保存を勝手に新規人生で上書きしない契約を守る。

これ以外の年齢/成長/親子/生活/血の系譜等の確定仕様も、戦闘移植の都合で削除・簡略化しない。文書と実装の相違や調整中の部分は、移植PRで出典と採否を明示する。

## 品質の判定と比較手順

比較は原型と変更後の正確なsource SHA・build・素材manifestに紐付ける。可変の最新DEVや、同時に変わる共有依存だけをBeforeに使わない。bkは重要な参照だが、共有依存も使うため、それだけで完全な描画固定を証明したことにはならない。

同じviewport、カメラ、actor/装備、seed、遭遇条件、経過時間を使い、待機・歩行/接近・通常攻撃・強い技・被弾・撃破/敗北・再開を動画と静止画で比べる。出生/年齢差や装備差、複数体は対応する段階で追加する。P0の原型はseed 73917だが、将来ゲーム乱数を移す際は消費順まで追跡する。高速forwardだけでhitstop等の実時間演出の検証を代替しない。

可愛さは自動pixel差分だけで合否を決めない。頭身/顔/輪郭、動作の滑らかさ、視認性、エフェクト遮蔽、音同期を各項目で確認し、既存の魅力が落ちた変更は修正して再比較する。ロジック改善を理由に見た目の後退を相殺しない。

性能は同一条件のフレーム時間、draw calls、三角形数、ロード量、メモリ、長時間での増加を記録する。目標はdesktop 60fps、Pixel Fold級の実機30fps。原型の実測を取り、追加機能で負荷を悪化させない予算を設定する。未測定の目標を達成済みと報告せず、headless/SwiftShader結果を実機FPS保証にしない。

スマホ縦・横とPixel Foldの閉/開、desktopで中央の視界、タイトル/メニューの折返し、5列選択、タップ、非表示/復帰、WebGL再作成、音の停止/復帰も確認する。

## 検証・採用・戻し方

P0では `apps/review/tests/johakyu-baseline.test.mjs` で原型のGit blob同一性を検査する。既存のframe/switcher、Lab、bkの検査は維持し、名称に関する期待値だけを新名称へ更新する。既存browser evidenceのタイトル期待値も更新するが、更新しただけでbrowser実行済みとはしない。

このP0同一性検査は原型を変えない初回専用の強い検査である。後続でruntimeを正当に変更するPRでは、**基準manifestを新実装のhashで塗り替えない**。変更対象の一律同一性検査を、同等以上の因果テストと固定Before/After証拠へ段階的に置き換える。bkの原型検査は残す。テストの削除や期待値の更新だけで品質劣化を通さない。

各PRは変更点、取り込んだ仕様の出典SHA/関数、未確定事項、原型との比較、ゲーム上の受入結果、保存互換、戻し方を記録する。見た目/操作を変える段階では局所browser証拠も残す。必要なfocused test/buildを既存Astra経路で選び、Fast DEVへ永続的なjob/stepや全件検査を追加しない。

問題が出た変更はその統合単位を修正またはrevertし、新側の最後に受入済みの実装へ戻す。無関係な改善や他者の変更を巻き戻さない。P6以降は保存の互換性/書き戻しの安全性も先に検証する。未受入の統合を本編既定へ切り替えず、Production/mainはこの計画作成では変更しない。

## 今回の実装範囲と次の着手単位

今回の変更セットは **P0の名称・計画・ソース保護の土台**。旧側の戦闘ルール、部位、スタミナ、技の習得、保存、本編切替はまだ変更しない。現行renderer、カメラ、モーション、戦闘テンポ、音、素材、bk本体を変更しない。

次の着手単位はP1: 旧側の確定/調整中/レビュー専用の差分台帳と、現在の演出へ副作用を出さない最小接続契約。P1の実装・検証が揃ってからP2へ進む。計画の存在や名称変更を、ゲーム仕様の移植完了として報告しない。
