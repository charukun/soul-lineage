# Reference-guided Facial Expression Workflow

表情参考画像の生成と、元の3Dモデルへのシェイプキー実装を別工程にする。2026-09-17のユーザー指定手法を、既存のキャラクター制作規約に組み込んだもの。

この文書は制作手順であり、表情アセットの実装済み証明ではない。[Character Modeling Standard](CHARACTER_MODELING.md) と対象モデルの契約を優先する。KayKit-first、ライセンス、既存rig/runtime、明示visual approval、Production gateを変更しない。3アプリの対象キャラクターに適用できるが、全モデルの一括置換やゲーム仕様変更は行わない。

## 1. 元データの確認と固定

最新developと対象モデル契約から、編集可能な正本の `.blend`、顔mesh、rig、既存shape keys、歯・舌・眼球・まつ毛、runtime export先を特定する。実在するデータを読み取り確認してから作業する。今回の対象ファイルや参照画像がない場合、生成済み・加工済みと扱わない。

元ファイルを保持し、別名の作業コピーを作る。source path、commit、ファイルhash、Blender version、対象object/mesh名、頂点数、頂点indexとedge/face接続、Basis、既存key名・値・相対参照、UV/material/weight/armatureを記録する。中立状態は元のBasisと契約上のneutral poseを正本とし、変更しない。

顔が板・テクスチャのみ、必要なまぶたや口内がない、変形に必要なtopologyがない場合は、その不足を記録する。必要な局所形状の準備は既存契約に従う別工程とし、準備後に基準を再固定して撮影する。名前だけのkey、別人への再生成、無断の全面retopologyで解決済みとしない。既存の離散表情を連続変形と呼び替えない。

## 2. 元モデルを4枚撮影する

同一のneutral、照明、材質、解像度、顔の画面内サイズを使う。正面と真横のcameraを固定し、比較にはorthographicを優先する。透視投影が必要な契約では焦点距離・距離も固定する。投影方式、camera transform、ortho scaleまたは焦点距離、左右どちらの側面かを記録する。

| 実モデルから取得する画像 | 内容 |
| --- | --- |
| `neutral-front-clean.png` | 正面、頂点・エッジ表示なし |
| `neutral-front-topology.png` | 同じ正面、実meshの頂点・エッジ表示あり |
| `neutral-side-clean.png` | 真横、頂点・エッジ表示なし |
| `neutral-side-topology.png` | 同じ真横、実meshの頂点・エッジ表示あり |

点と線はBlenderの実meshから取得する。見やすさのため顔以外を隠す場合は撮影時だけのvisibility変更とし、元アセットを削除しない。modifier表示と編集対象meshの違いを記録し、subdivision後の表示点を元meshの頂点indexと混同しない。

## 3. 表情の参考画像を生成する

上の4枚を入力として、最初は笑顔の正面・真横を作る。顔立ち、頭蓋・顎の比率、目鼻の配置、髪、材質、cameraを保ち、口角・頬・まぶたなど表情に必要な差だけを指定する。点・線入りの生成見本も形状検討に使えるが、すべて `GENERATED_REFERENCE_ONLY` と識別し、実モデル撮影と別に保存する。

**生成画像の点・線は頂点IDや正確なtopologyではない。** 点の個数・並びをコピーしたり、2Dの点から3D座標が確定したと扱ったりしない。正面と側面で形が食い違う場合は元モデルの構造とidentityを優先し、参考画像側を修正する。参考画像を完成mesh・実Blender画面・runtime改善の証拠として報告しない。

ユーザー提示のGPT-Image2.5等は参考画像を作る手段であり、特定providerやAPIの必須依存にはしない。利用できる既存の画像生成経路を使い、モデル名・設定・入力画像hash・指示文を実際に分かる範囲で記録する。不明値を捏造しない。追加有料API、新規課金、外部サービスへのモデルuploadをこの手法だけで許可されたと扱わない。

### 参考画像工程への指示テンプレート

> 添付は同じ元モデルの無表情を撮影した正面・真横、各clean/topologyの4枚。顔立ち・比率・髪・材質・投影条件を保ち、指定した表情の正面と真横を作成する。口角、頬、まぶたの変化を両方向で整合させる。点・線を描く場合も形の説明用であり、実meshや頂点対応の保証ではない。成果はGENERATED_REFERENCE_ONLYとして区別する。

## 4. 元メッシュへシェイプキーを実装する

参考画像をいったん固定し、元 `.blend` の作業コピーだけを編集する。実頂点・実edge loopを選んで局所変形する。画像への全面置換、画像からの別mesh生成、生成された点を頂点indexへ自動対応させる処理はこの工程に含めない。

- Basis、頂点数・順序・edge/face接続、既存UV/material/weight/armature/keyを維持する。remesh、頂点追加削除、無断のmodifier適用は行わない。変形前後のtopologyとBasisを比較し、意図しない変更があれば修正する。
- 既存命名・相対key・表情mappingに合わせて追加する。既存keyを上書きせず、mouth corner / cheek / eyelid等の変更域を記録する。Basisからの相対keyを新設する場合、他keyの意図しない評価結果を焼き込まない。
- 口唇の厚み、頬の体積、まぶたと眼球、歯・舌と口内の位置関係を確認する。jaw boneとmorphを併用する場合は既存rigの役割に合わせ、顎を二重に動かさない。

### メッシュ工程への指示テンプレート

> 参考画像は見た目の目標であり、実頂点の対応表ではない。正本モデルの作業コピーで、口角・頬・まぶた等の既存頂点だけを局所調整してシェイプキーを追加する。元の顔立ち、Basis、topology、UV、材質、rig、既存表情を保持する。歯・舌・眼球との関係を正面と真横で検査し、必要な変更と未解決点を記録する。元データは上書きしない。

## 5. 中間形状と組み合わせを実モデルで検査する

各追加keyを最低 `0.0 / 0.5 / 1.0` で、固定した正面・真横から確認する。さらに `0.25 / 0.75` と斜めからの確認を行い、`0 → 1 → 0` の短い実モデル動画で補間の破綻を探す。静止画・有限サンプルだけで全範囲の無破綻を保証したとは扱わない。

検査対象はidentityの維持、口角の引きつれ、頬の潰れ、口唇やまぶたの貫通、歯・舌の突出、口内の隙間、閉眼時の眼球露出、まつ毛追従、意図しない左右差、neutralへの完全な復帰。自動のtopology/Basis比較と目視変形検査は分けて記録する。

追加したものと既存のものを含む、runtimeで使用する表情の組み合わせも検査する。代表例は笑顔+瞬き、母音口形+感情、顎動作+口形。排他制御がある組は、その制御が実際に効くことを確認する。単体keyの合格を混合時の合格へ読み替えない。既存の関係ない表情・頭部動作も変更域に応じて回帰確認する。

問題のある部位・key・値・viewを記録し、合格済み部分を保持して局所修正する。既存の最大3回のrefinement loopに従い、残る不具合を未解決として示す。生成画像を作り直すだけでmesh修正済みとしない。

## 6. 表情を増やし、書き出し後も確認する

笑顔の工程が成立したら、必要な範囲で左右の瞬き、`あ・い・う・え・お` の母音口形、喜怒哀楽等へ同じ工程を繰り返す。key名は例示ではなく実runtimeの既存mappingに従い、生成した候補と実装・検証済みの表情を区別する。

GLB等へ書き出す際は、対象exporter/runtimeが必要なmorph、skin、animationを保持するか確認する。実際のrepository loaderで読み込み、key mapping、neutral、中間値、混合、既存motionを再検査する。Blenderだけで動くdriverやrig制御は、export後にも再現されるかを実データで確認し、未対応なら不足を明示する。

既存の軽量化・端末budgetを維持する。追加target数、対象頂点数、asset byte sizeと実行時負荷を比較する。共有のauthoring手順を使うことは、全NPC・全距離で全表情を常時計算する指示ではない。LODや更新頻度は既存runtime契約に従い、未計測のゼロコストや実機fpsを保証しない。

## 7. 保存・受入証拠

元 `.blend` を残し、例として `<asset>_expressions_vNN.blend` のような別名で保存する。対象アセット契約の格納先を使い、第二のアセット正本や長期review branchを作らない。

成果は、元モデルの4枚、生成参考、実meshのbefore/after・中間値・混合検査、runtime検査を混ぜずに管理する。PRにはsource/outputのpath・hash、追加/変更key、試した値・view・組み合わせ、固定camera、topology/Basisの比較結果、実モデルの画像/動画、runtime結果、未確認範囲を記録する。生成参考への承認を実モデルのvisual approvalに置き換えない。

この手順を文書として追加しただけのPRでは、モデル・参考画像・シェイプキーが未作成であることを明記する。実際のモデル制作では、[Visual Review](VISUAL_REVIEW.md) と対象キャラクターの受入条件を満たしてから表情完成を報告する。
